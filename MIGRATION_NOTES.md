# Заметки о переносе

Технические заметки о том, что изменено при выделении сервиса из исходного
проекта в самостоятельный публичный репозиторий. Астрологическая логика
(орбисы, система домов, состав точек, формулы расчёта) не менялась — это
отдельный этап, требующий согласования с астрологом.

## Что изменено

- **Зависимости запинены точно.** `kerykeion==5.12.8`, `pyswisseph==2.10.3.2`
  и остальные пакеты из `requirements.txt` зафиксированы на конкретных
  версиях, проверенных на совместимость друг с другом и с Python 3.11
  (включая наличие готовых wheel-пакетов для `manylinux`/`cp311` у бинарных
  расширений `pyswisseph`, `timezonefinder`, `psycopg[binary]` и их
  транзитивных зависимостей).
- **Добавлен `Dockerfile`** под Timeweb Cloud App Platform: multi-stage
  сборка (`builder` с `gcc`/заголовками для компиляции нативных расширений,
  затем чистый `runtime`-образ `python:3.11-slim`), непривилегированный
  пользователь, порт из `$PORT` с фолбэком `8000`. Добавлен `.dockerignore`,
  чтобы `.env`, `.git` и прочее не попадали в образ.
- **Убрана зависимость от Supabase.** `geocoder.py` больше не ходит в
  Supabase REST напрямую и не требует `SUPABASE_URL`/`SUPABASE_KEY` при
  импорте (в исходной версии их отсутствие приводило к `KeyError` уже на
  старте — сервис не мог работать даже в режиме «координаты переданы явно»).
  Доступ к справочнику городов вынесен за интерфейс `CityRepository`
  (`city_repository.py`):
  - `NullCityRepository` — заглушка по умолчанию, если справочник не
    сконфигурирован; возвращает понятную ошибку (`503`) вместо падения.
  - `PostgresCityRepository` — рабочая реализация поиска по префиксу с
    учётом альтернативных (в т.ч. исторических) названий, поверх таблиц
    `cities`/`city_alternate_names` (`migrations/001_cities.sql`),
    заполняемых из GeoNames (`scripts/import_geonames.py`). Подробности —
    в README, раздел «Справочник городов (GeoNames)», и в
    `docs/adr/0001-own-postgres-city-directory.md`.
  - Источник выбирается через `CITY_REPOSITORY_SOURCE`.
  - Геокодирование одного города через Nominatim (`get_coordinates`) и
    определение таймзоны через `timezonefinder` не связаны со справочником
    и работают как раньше — это отдельный путь, не требующий БД.
  - Расчётные эндпоинты (`/calculate`, `/natal/svg`, `/transits`,
    `/synastry`) не зависят от справочника вообще: если координаты и
    таймзона переданы в запросе явно, обращения к БД не происходит.
- **Startup-проверка `SERVICE_SECRET`** — поведение не менялось (оно уже
  было корректным в исходном коде): в production без `SERVICE_SECRET`
  сервис не стартует, в `ENVIRONMENT=development` — стартует без секрета.
  Реальное значение секрета из исходного проекта в `.env.example` не
  переносилось.
- **`.env.example` пересобран** под фактически используемые сервисом
  переменные: `ENVIRONMENT`, `SERVICE_SECRET`, `CITY_REPOSITORY_SOURCE`,
  `CITY_REPOSITORY_DSN`. Значения — плейсхолдеры, без реальных секретов.
- **Добавлены `.gitignore`, `LICENSE` (полный текст AGPL-3.0), `README.md`.**

## Что намеренно не перенесено

- Прямая интеграция с Supabase (REST-клиент, `SUPABASE_URL`/`SUPABASE_KEY`) —
  заменена на адаптер с явно выбираемым источником.
- Любые значения секретов, ключей и DSN из исходного проекта — в публичный
  репозиторий переносить нельзя, все значения в `.env.example` — плейсхолдеры.
- Таблица `cities` из исходного Supabase-проекта и её данные — не
  переносились. Новая таблица `cities` (см. `migrations/001_cities.sql`)
  заполняется независимо из открытого дампа GeoNames, а не копированием
  старых данных.

## Тесты, фиксирующие текущее поведение

Добавлен `tests/` — регрессионный барьер перед будущими изменениями
логики. Тесты описывают поведение сервиса **как есть**, а не как оно
должно быть; там, где поведение выглядит неидеальным, это зафиксировано
явно, а не подогнано под желаемый результат. Подробности и список
файлов — в README, раздел «Тесты». Зависимости для тестов (`pytest`,
`httpx`) вынесены в `requirements-dev.txt`, в основной `requirements.txt`
не добавлялись.

При написании тестов обнаружены и намеренно НЕ исправлены (логика не
менялась):

- **`Mean_Node` заявлен, но не считается.** `calculator.PLANET_ATTRS`
  ссылается на точку `Mean_Node` через атрибут `mean_node`, но объект,
  который отдаёт `AstrologicalSubjectFactory` в используемой версии
  kerykeion (`5.12.8`), такого атрибута не имеет (есть
  `mean_north_lunar_node` и `true_north_lunar_node`, но не `mean_node`).
  `_planets()` тихо пропускает точку, для которой `getattr(...) is None`,
  поэтому в ответе `/calculate` из 14 заявленных точек (13 из
  `PLANET_ATTRS` + отдельно вычисляемая `Selena`) фактически присутствует
  13 — `Mean_Node` отсутствует без какой-либо ошибки или предупреждения.
  Зафиксировано тестом `tests/test_points_completeness.py` как
  `xfail(strict=True)`.
- **Ошибки валидации входных данных возвращают `500`, а не `422`.**
  `POST /calculate` разбирает `birth_date`/`birth_time` через `int(p) for
  p in ...split(...)` без валидации и без обработки исключений;
  несуществующая таймзона также не проверяется. Некорректная дата,
  некорректное время и несуществующая таймзона приводят к необработанному
  исключению → FastAPI отдаёт `500 Internal Server Error` вместо `422
  Unprocessable Entity`. Зафиксировано тестами в
  `tests/test_api_contract.py`.

Оба пункта — кандидаты на исправление на следующем этапе, но не в рамках
этой технической подготовки.
