# Kokon Astro Engine

Расчётный сервис астрологии для проекта «Кокон». Автономный HTTP API поверх
[kerykeion](https://www.kerykeion.net/) и Swiss Ephemeris: натальные карты,
транзиты, синастрия и SVG-отрисовка карты. Сервис не хранит данные
пользователей — все расчёты выполняются на лету по переданным в запросе
данным.

## Назначение

- `GET /health` — проверка живости.
- `GET /geocode/search` — автодополнение городов (требует настроенного
  справочника, см. [«Переменные окружения»](#переменные-окружения)).
- `POST /calculate` — натальная карта: планеты, дома, аспекты.
- `POST /natal/svg` — натальная карта в виде SVG-изображения.
- `POST /transits` — активные транзиты на заданную дату относительно
  натальной карты.
- `POST /synastry` — совместимость двух натальных карт.

Все расчётные эндпоинты принимают координаты (`birth_lat`/`birth_lng`) и
таймзону (`timezone`) напрямую в теле запроса. Справочник городов нужен
только для UI-автодополнения (`/geocode/search`) и не участвует в самом
расчёте.

Астрологическая логика (орбисы, система домов, состав точек, формулы) — вне
рамок текущей технической подготовки и переносится как есть, без изменений.

## Требования

- Python 3.11
- См. точные версии зависимостей в `requirements.txt`

`pyswisseph` и `timezonefinder` — расширения с нативным кодом; для установки
из исходников нужны компилятор C и заголовки Python (см. `Dockerfile`, стадия
`builder`). Если для вашей платформы существуют готовые wheel-пакеты, сборка
не потребуется.

## Локальный запуск

```bash
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env
# отредактируйте .env при необходимости

uvicorn main:app --reload
```

По умолчанию сервис слушает `http://127.0.0.1:8000`.

Для локальной разработки без секрета аутентификации задайте
`ENVIRONMENT=development` в `.env` — тогда отсутствие `SERVICE_SECRET` не
приведёт к падению при старте, а эндпоинты будут доступны без заголовка
`X-Service-Secret`.

## Тесты

Тесты фиксируют **текущее** поведение сервиса (включая известные дефекты)
как регрессионный барьер перед будущими изменениями логики — это не
проверка астрологической корректности расчётов.

Зависимости для тестов вынесены в отдельный `requirements-dev.txt` (pytest,
httpx), чтобы не тянуть их в продовый образ:

```bash
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt

pytest tests/ -v
```

Состав тестов (`tests/`):

- `test_natal_golden.py` — golden-тест: расчёт натальной карты для
  эталонных входных данных (1990-06-15, 14:30, 55.7558/37.6173,
  Europe/Moscow) сравнивается с сохранённой фикстурой
  `tests/fixtures/natal_1990_06_15_moscow.json`. Числа сравниваются с
  допуском `1e-6`, а не на точное равенство.
- `test_points_completeness.py` — сверяет полный список точек, которые
  сервис заявляет считать (`calculator.PLANET_ATTRS` + Selena), со
  списком точек в фактическом ответе. Помечен `xfail(strict=True)`:
  сейчас в ответе не хватает `Mean_Node` (расхождение имени атрибута
  между `calculator.py` и используемой версией `kerykeion` — подробности
  в докстринге теста и в `MIGRATION_NOTES.md`). Если дефект когда-нибудь
  устранят, тест провалится как XPASS — это сигнал снять маркер.
- `test_api_contract.py` — контракт `POST /calculate`: валидный запрос
  возвращает `200`; некорректная дата, некорректное время и
  несуществующая таймзона фактически возвращают `500` (необработанное
  исключение, а не `422`) — так ведёт себя код сейчас.
- `test_city_repository_unconfigured.py` — расчёт с явно переданными
  координатами и таймзоной работает без настроенного справочника городов;
  `/geocode/search` в этом случае отдаёт `503`.
- `test_postgres_city_repository.py` — интеграционные тесты
  `PostgresCityRepository` (поиск «Москва» находит российскую столицу
  первой, «Петербург» находит «Санкт-Петербург» по подстроке, «Ленинград»
  находит его же по историческому имени, маленький посёлок находится по
  точному названию, и т.д. — см. раздел
  [«Справочник городов (GeoNames)»](#справочник-городов-geonames)).
  Требуют настоящий PostgreSQL и **пропускаются**, если не задана
  переменная `TEST_POSTGRES_DSN` — обычные `pytest tests/ -v` их не
  затронут.
- `test_import_geonames_idempotency.py` — идемпотентность
  `scripts/import_geonames.py` на синтетических данных в формате
  GeoNames: повторный запуск не дублирует строки, изменившиеся строки
  обновляются, пропавшие из дампа — удаляются (включая каскадное удаление
  альтернативных названий вместе с городом), а сбой на середине импорта не
  оставляет таблицу пустой/неполной. Тоже требует `TEST_POSTGRES_DSN`.

## Справочник городов (GeoNames)

Данные для автодополнения (`GET /geocode/search`) — из
[GeoNames](https://www.geonames.org/): файлы `cities500.txt` (города) и
`alternateNamesV2.txt` (названия на разных языках, включая исторические)
из [дампов GeoNames](https://download.geonames.org/export/dump/).

**Лицензия данных: [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/).
Атрибуция обязательна** — она приведена в разделе [«Лицензия»](#лицензия)
ниже; сами дампы в репозиторий не входят (см. `.gitignore`) и скачиваются
отдельно.

### Как запустить импорт

1. Скачайте и распакуйте `cities500.zip` и `alternateNamesV2.zip` с
   https://download.geonames.org/export/dump/ в какой-нибудь каталог
   (по умолчанию скрипт ищет `~/Desktop/Кокон Claude/geonames-data/`).
2. Примените миграции схемы к базе, на которую указывает
   `CITY_REPOSITORY_DSN` (по порядку номеров):
   ```bash
   psql "$CITY_REPOSITORY_DSN" -f migrations/001_cities.sql
   psql "$CITY_REPOSITORY_DSN" -f migrations/002_trigram_search.sql
   ```
3. Убедитесь, что `CITY_REPOSITORY_DSN` задан в `.env` (зависимости для
   импорта — `psycopg`, `python-dotenv` — уже в `requirements.txt`).
4. Запустите импорт:
   ```bash
   python scripts/import_geonames.py [путь_к_каталогу_с_дампами]
   ```
   Скрипт грузит из `cities500.txt` только населённые пункты
   (`feature_code`, начинающийся с `PPL`, кроме заброшенных/уничтоженных/
   переставших существовать `PPLQ`/`PPLW`/`PPLH`) — по размеру НЕ
   фильтрует, маленькие посёлки остаются наравне со столицами (см.
   [ADR-0002](docs/adr/0002-import-filters-by-place-type-not-size.md)).
   Из `alternateNamesV2.txt` берёт только записи для загруженных городов
   на языках `ru`/`en`, плюс записи с признаком исторического названия на
   любом языке (например, «Ленинград» для Санкт-Петербурга). Файл
   читается потоково (без загрузки целиком в память), загрузка — через
   `COPY`.

   Импорт **идемпотентен через upsert, а не через TRUNCATE**: каждая
   таблица грузится через `COPY` во временную staging-таблицу, затем
   переносится в целевую через `INSERT ... ON CONFLICT DO UPDATE`, и в
   конце `DELETE` убирает строки, которых больше нет в текущем дампе.
   TRUNCATE намеренно не используется — он держит блокировку на всё время
   импорта (блокируя `/geocode/search`) и делает частичный сбой
   разрушительным: прерванный на середине TRUNCATE-импорт мог бы оставить
   таблицу пустой. С upsert'ом другие запросы всегда видят либо полностью
   старые, либо полностью новые данные, а повторный запуск (в т.ч. после
   сбоя, в любой момент) безопасен и не создаёт дубликатов. `cities` и
   `city_alternate_names` коммитятся отдельно, каждая по завершении своего
   upsert — сбой на второй таблице не откатывает уже загруженную первую.
5. Установите `CITY_REPOSITORY_SOURCE=postgres` в `.env`, чтобы сервис
   начал использовать заполненный справочник.

### Как ранжируется поиск

`GET /geocode/search` ищет в два тира (`PostgresCityRepository` в
`city_repository.py`):

1. **Префиксные совпадения** («начинается с») — всегда выше тира 2.
2. **Совпадения по подстроке** («содержит») — нужны для русских составных
   названий, где часто ищут по значимой части, а не с начала строки:
   «Петербург» находит «Санкт-Петербург», «Новгород» — «Нижний Новгород».

Внутри каждого тира — приоритет городам, совпавшим по названию,
помеченному в GeoNames как предпочтительное (`city_alternate_names.is_preferred`),
затем — сортировка по населению по убыванию. Показываемое имя всегда
современное (из `cities` + предпочтительное русское альтернативное имя),
даже если само совпадение произошло по историческому названию.

Обоснование индексов — в комментариях к `migrations/001_cities.sql`
(префиксный поиск, btree + `text_pattern_ops`) и
`migrations/002_trigram_search.sql` (поиск по подстроке, `pg_trgm`).
Решения задокументированы как ADR:

- [ADR-0001](docs/adr/0001-own-postgres-city-directory.md) — почему
  справочник городов хранится в собственном PostgreSQL, а не за внешним
  геокодером.
- [ADR-0002](docs/adr/0002-import-filters-by-place-type-not-size.md) —
  почему импорт фильтрует по типу населённого пункта, но не по размеру.
- [ADR-0003](docs/adr/0003-trigram-search-for-substring-matching.md) —
  почему добавлены триграммы поверх (не вместо) индексов ADR-0001;
  уточняет ADR-0001, а не отменяет.

## Переменные окружения

| Переменная               | Обязательна            | Описание                                                                                                   |
|---------------------------|-------------------------|--------------------------------------------------------------------------------------------------------------|
| `ENVIRONMENT`              | нет (default: production) | `development` отключает обязательность `SERVICE_SECRET` при старте.                                        |
| `SERVICE_SECRET`           | да в production           | Секрет для аутентификации запросов, сверяется с заголовком `X-Service-Secret`.                              |
| `CITY_REPOSITORY_SOURCE`   | нет                        | Источник справочника городов для `/geocode/search`: `postgres` или пусто (справочник недоступен, `503`).    |
| `CITY_REPOSITORY_DSN`      | да, если `CITY_REPOSITORY_SOURCE=postgres` | Строка подключения к PostgreSQL — используется и сервисом, и `scripts/import_geonames.py`.                    |
| `TEST_POSTGRES_DSN`        | нет, только для тестов     | Отдельная строка подключения к ОДНОРАЗОВОЙ/тестовой БД для `tests/test_postgres_city_repository.py` — тесты делают `TRUNCATE`, поэтому НЕ используйте здесь `CITY_REPOSITORY_DSN` от реальной базы. |
| `PORT`                     | нет (default: 8000)       | Порт, на котором слушает `uvicorn`. Задаётся платформой деплоя (Timeweb Cloud App Platform подставляет её автоматически). |

Полный список — в `.env.example`.

## Деплой

Сервис рассчитан на деплой через Docker на Timeweb Cloud App Platform (или
любую другую платформу, поддерживающую Dockerfile).

`Dockerfile` — multi-stage:

1. **builder** (`python:3.11-slim` + `gcc`, заголовки Python) — собирает
   зависимости с нативными расширениями (`pyswisseph`, транзитивные
   зависимости `timezonefinder`).
2. **runtime** (`python:3.11-slim`, без компилятора) — копирует готовые
   пакеты, запускает сервис от непривилегированного пользователя.

Порт берётся из переменной `$PORT` с фолбэком на `8000`:

```
CMD ["sh", "-c", "uvicorn main:app --host 0.0.0.0 --port ${PORT:-8000}"]
```

Локальная сборка и запуск:

```bash
docker build -t kokon-astro-engine .
docker run --rm -p 8000:8000 --env-file .env kokon-astro-engine
```

Обязательно задайте `SERVICE_SECRET` в переменных окружения платформы —
без `ENVIRONMENT=development` сервис не запустится без него.

угловой секунды — этого достаточно для астрологических расчётов в рамках
проекта «Кокон».
