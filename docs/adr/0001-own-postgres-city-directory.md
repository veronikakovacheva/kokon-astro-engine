# ADR 0001: справочник городов — собственный PostgreSQL, а не внешний геокодер

## Статус

Принято.

## Контекст

`GET /geocode/search` — автодополнение города для UI (ввод «Мос...» →
список городов с координатами и таймзоной). Это отдельный путь от
собственно расчёта: `POST /calculate` и другие расчётные эндпоинты
принимают координаты и таймзону явно и от справочника не зависят (см.
`city_repository.py`, `NullCityRepository`).

Ранее (в проекте, откуда сервис был выделен) автодополнение ходило в
Supabase REST за таблицей городов. При выделении сервиса эта прямая
зависимость была вынесена за интерфейс `CityRepository`, и встал вопрос,
чем backing store для автодополнения быть дальше. Рассматривались два
пути:

1. **На каждый запрос автодополнения дёргать внешний геокодер**
   (например, Nominatim — он уже используется в `geocoder.get_coordinates`
   для геокодирования одного города по названию, отдельный путь, не
   меняется этим решением).
2. **Держать собственную таблицу городов в PostgreSQL**, заполненную из
   открытого дампа, и искать по ней.

Требования к автодополнению:
- отклик на уровне десятков миллисекунд на каждое нажатие клавиши;
- работа с русскими названиями, включая исторические (например,
  «Ленинград» должен находить Санкт-Петербург);
- предсказуемое ранжирование (крупный город — выше тёзки с маленьким
  населением, см. кейс «Москва» RU vs «Moscow» в США/Ирландии);
- не зависеть от доступности и политики стороннего сервиса в горячем
  пути пользовательского ввода.

## Решение

Справочник городов для автодополнения хранится в собственном PostgreSQL
(`cities` + `city_alternate_names`, миграция `migrations/001_cities.sql`),
заполняется офлайн-скриптом (`scripts/import_geonames.py`) из открытого
дампа [GeoNames](https://www.geonames.org/) (`cities500.txt` +
`alternateNamesV2.txt`, лицензия CC BY 4.0, атрибуция — см. README).
`PostgresCityRepository` ищет по префиксу с учётом альтернативных
(в т.ч. исторических) названий и сортирует по населению.

Геокодирование Nominatim (`geocoder.get_coordinates`) — обращение к
внешнему сервису для одного конкретного города — этим решением не
затрагивается: это отдельный, гораздо более редкий путь (один запрос на
пользователя при вводе города вручную без выбора из автодополнения), а не
поток запросов на каждое нажатие клавиши.

## Обоснование

- **Латентность и объём запросов.** Автодополнение стреляет на каждое
  нажатие клавиши — это на порядки чаще, чем один геокодинг на пользователя.
  Локальный индексированный `LIKE 'prefix%'` по своей БД — миллисекунды;
  внешний HTTP-геокодер на такой поток не рассчитан.
- **Политика использования внешних геокодеров.** У большинства бесплатных
  геокодеров (в т.ч. Nominatim) есть строгие лимиты (порядка 1 запроса в
  секунду, требование кэширования, запрет на автодополнение "на лету" по
  условиям использования) — не совместимо с автодополнением как
  паттерном доступа.
- **Контроль над данными.** Нужны русские названия и исторические
  варианты («Ленинград» → современный Санкт-Петербург) с точным
  соответствием, а не что вернёт сторонний сервис в конкретный момент.
  Собственная таблица `city_alternate_names` с явными флагами
  `iso_language`/`is_historic`/`is_preferred` даёт это напрямую.
- **Независимость и предсказуемость.** Нет внешней точки отказа в
  горячем пути пользовательского ввода; результаты воспроизводимы и не
  меняются из-за обновлений стороннего сервиса.
- **Лицензия источника данных.** GeoNames — CC BY 4.0, разрешает
  self-hosting и обработку при условии атрибуции; это делает вариант
  «свой справочник» юридически чистым и не требующим коммерческой
  подписки (в отличие от многих платных геокодеров с API-ключами).

## Последствия

- Появляется собственный ETL-шаг: дамп GeoNames нужно периодически
  обновлять и перезаливать (`scripts/import_geonames.py` — полная
  замена, идемпотентно), что требует ручного/scheduled запуска — это
  эксплуатационная нагрузка, которой не было бы при обращении к внешнему
  сервису.
- Качество и полнота данных ограничены дампом GeoNames и тем, какие
  языки/исторические названия отобраны при импорте (сейчас — `ru`/`en` +
  исторические любого языка, см. `scripts/import_geonames.py`); расширение
  списка языков потребует повторного импорта, а не просто смены
  провайдера.
- Обязательна атрибуция GeoNames в публичных материалах сервиса (условие
  CC BY 4.0) — выполнено в README.md.
- Подключение к БД на каждый вызов `PostgresCityRepository.search_cities`
  открывается заново (без пула соединений) — приемлемо на первом этапе,
  но при росте нагрузки на `/geocode/search` может понадобиться пул
  соединений (например, через `psycopg_pool`); в рамках этого решения не
  реализовано.
