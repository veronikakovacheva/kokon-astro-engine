# ADR 0003: pg_trgm для поиска по подстроке — уточнение ADR-0001, не отмена

## Статус

Принято. Уточняет
[ADR-0001](0001-own-postgres-city-directory.md) и опирается на неё же:
0001 обосновала, ПОЧЕМУ справочник городов живёт в собственном
PostgreSQL, а не за внешним геокодером; здесь речь только о том, КАКИЕ
индексы нужны внутри этой уже принятой архитектуры для нового паттерна
поиска. Это ADR **не отменяет и не заменяет** [ADR-0001](0001-own-postgres-city-directory.md)
и её же собственную миграцию 001 (там же было явно решено НЕ добавлять
pg_trgm — см. комментарий в `migrations/001_cities.sql`); это решение —
следующий шаг по мере того, как определился более широкий набор
требований к поиску.

## Контекст

В миграции 001 (см. её комментарий и `docs/adr/0001-own-postgres-city-directory.md`)
для автодополнения был выбран btree с operator class `text_pattern_ops`
вместо триграмм pg_trgm — обоснованно, потому что на тот момент
единственным требованием был чистый префиксный поиск ("начинается с X"),
для которого этот индекс эффективнее pg_trgm и дешевле в обслуживании.

На практике выяснилось, что для русских составных топонимов префиксного
поиска недостаточно: пользователи часто вводят значимую часть названия, а
не начало строки целиком. «Петербург» должен находить «Санкт-Петербург»,
«Новгород» — «Нижний Новгород». Это не редкий крайний случай, а типичный
способ ввода для целого класса русских городских названий (двухсоставные
имена, где первое слово — уточняющее: Санкт-, Нижний, Великий, Ростов-на-
и т.п.).

Обычный btree-индекс — с `text_pattern_ops` или без — физически не может
ускорить `LIKE '%x%'`: его порядок сортировки полезен только для
LEFT-anchored шаблонов (`x%`). Для поиска подстроки где угодно в строке
единственный способ ускорить `LIKE`/`ILIKE` через индекс в PostgreSQL —
триграммный индекс (`pg_trgm`, operator class `gin_trgm_ops`/`gist_trgm_ops`).

## Решение

Добавлена отдельная миграция `migrations/002_trigram_search.sql`:
`CREATE EXTENSION pg_trgm` + GIN-индексы по `lower(name)`,
`lower(ascii_name)` (в `cities`) и `lower(alternate_name)` (в
`city_alternate_names`). Индексы из миграции 001 (`text_pattern_ops`) не
удаляются и не заменяются — они остаются лучшим выбором для префиксного
поиска.

`PostgresCityRepository.search_cities` (`city_repository.py`) теперь ищет
в два тира: сначала префиксные совпадения (используют индексы
миграции 001), затем — совпадения по подстроке среди городов, ещё не
найденных на первом тире (используют триграммные индексы миграции 002).
Внутри каждого тира приоритет — предпочтительным названиям
(`city_alternate_names.is_preferred`), затем — населению по убыванию.
Префиксные совпадения всегда выше совпадений по подстроке — префиксное
совпадение обычно точнее выражает намерение пользователя (ввод с начала
слова), а не просто содержит совпавшие буквы где-то внутри.

## Обоснование

- **Два разных паттерна доступа — два разных индекса.** ADR-0001/
  миграция 001 закрывали конкретный, на тот момент единственный, паттерн
  (LEFT-anchored). Появление второго паттерна (contains) не делает первое
  решение неверным — оно по-прежнему верно для своей задачи. Правильный
  ответ на "появился новый паттерн доступа" — добавить индекс под него,
  а не заменить существующий.
- **pg_trgm — единственный практичный способ ускорить LIKE '%x%' в
  PostgreSQL.** Альтернатива (полнотекстовый поиск `tsvector`/`tsquery`)
  избыточна: она токенизирует по словам и плохо подходит для поиска
  произвольной подстроки ВНУТРИ слова/составного топонима (например,
  «бург» как часть «Петербург» — не отдельное слово).
  full-text search такой запрос не обслужит без дополнительного стемминга
  под конкретный язык, чего сейчас не требуется.
- **Ранжирование "префикс выше подстроки" соответствует ожиданиям
  пользователя.** Если ввод буквально совпадает с началом названия — это
  обычно более уверенное совпадение, чем "название где-то содержит эти
  буквы". Формализовано как двухуровневый `ORDER BY` (тир, затем
  предпочтительность, затем население), а не как единая оценка
  релевантности — проще проверить и объяснить, чем ML-подобный скоринг.

## Последствия

- Индексов на `cities`/`city_alternate_names` стало больше (btree
  `text_pattern_ops` из 001 + GIN `gin_trgm_ops` из 002 на тех же
  колонках) — это увеличивает объём на диске и стоимость `INSERT`/`UPDATE`
  при импорте (upsert в `scripts/import_geonames.py` теперь поддерживает
  вдвое больше индексов на запись), но не стоимость самого поиска —
  наоборот, каждый тир использует свой более быстрый индекс вместо одного
  компромиссного.
- Запрос поиска стал сложнее (два тира, агрегация `is_preferred` через
  `bool_or`, см. `PostgresCityRepository._SEARCH_SQL`) — это осознанный
  компромисс читаемости ради корректного ранжирования; логика
  задокументирована в докстринге класса и в этом ADR.
- GIN-индексы pg_trgm дороже перестраивать при большом объёме изменений,
  чем btree — при периодическом полном обновлении справочника
  (`scripts/import_geonames.py`) это увеличивает время upsert-фазы; на
  объёме в сотни тысяч строк это по-прежнему на уровне десятков секунд,
  не часов, и не является практическим ограничением на данный момент.
